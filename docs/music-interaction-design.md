# Music interaction design and cross-platform contracts

Status: design only (task `nj3`, Music U01). Nothing in this document is
implemented yet. Dependent tasks implement and verify it; the per-candidate
interaction and verification map is in
[music-candidate-map.md](music-candidate-map.md).

This document is self-contained. The candidate IDs (M01–M71, F01–F03, A01–A10)
come from the music gap inventory of 2026-10-20 (Navidrome 0.64.2, DSub2000
5.7.5, Tempo 3.9.0 compared with Player at `5040cfb`). Each ID is restated with
its scope in the candidate map, so implementers do not need the inventory.

## 1. Goals and constraints

- Add a music library, an independent playback queue and playlists to Player
  **without a second UI**. Music views reuse the current header, sidebar,
  card grid, `.media-row` list rows, modal dialogs, floating player, toasts and
  `theme.css` tokens on the web, and the current Material 3 scaffolds, drawer,
  cards and `theme_provider.dart` color schemes on Android.
- Everything that already works stays as it is: sets/folders browsing, video,
  images, podcasts, lyrics, file favorites, notes, tags, bookmarks, resume,
  manual downloads, Android speed, local files, multiple servers and the
  current Chrome/Android casting.
- Every feature must work in Google Chrome, Mozilla Firefox and the native
  Android app (root `AGENTS.md`). Inherently Android-only integrations are
  listed in §11 with the shared part that the web must still verify.
- Web: keyboard first, vi-style navigation, visible focus, native typing,
  pointer/touch alternatives, no drag-only interaction (`player-server/AGENTS.md`).
- Android: touch and menu driven, labeled controls, tap targets of at least
  48 dp, screen-reader semantics, predictable Back, no hidden gestures as the
  only path (`player-android/AGENTS.md`).
- Podcasts are owned by the podcast plan (`docs/podcast-management-plan.md`)
  and the identity/sync contract (`docs/podcast-sync-contract.md`, task `uh3`).
  This design does not change podcast identity, episode state or sync (§10).

## 3. Design principles applied to music

1. **One library, two lenses.** *Sets* remain the file lens. *Music* is a new
   lens over the same audio files (albums, artists, songs, playlists). Nothing
   moves; a file is reachable both ways and keeps one identity (media id).
2. **Primary action is obvious, the rest is progressive.** The primary action
   of any music item is *Play* (Enter / tap). Secondary actions live in the
   existing action menu (`a`, ⋮, context menu), never as an always-visible
   button row.
3. **Selection is not playback.** Moving selection or browsing never changes
   what plays next. Only explicit actions (Play, Play next, Add to queue,
   queue edits) change the queue.
4. **Every reorder has a non-drag path.** Move up / Move down / Play next as
   menu items and keys; drag is an optional pointer enhancement.
5. **Undo instead of confirm for reversible edits** (queue remove/clear,
   playlist remove): a toast/snackbar with *Undo*. Confirm only destructive,
   hard-to-undo actions (delete playlist, revoke share, delete offline copies).
6. **Honest states.** Loading, empty, error, offline, permission and partial
   results are spelled out per screen (§9); unsupported platform features
   are explained, not hidden behind a dead button.

## 4. Information architecture

```
Library (existing app shell)
├── Music                         ← new lens (web sidebar section, Android drawer section)
│   ├── Home        (M38/M39: recently added/played, most played, random, favorites, pinned playlists)
│   ├── Albums      (M02/M04/M05/M09)  → Album detail → song rows
│   ├── Artists     (M03/M10/M40/M41)  → Artist detail → albums, top songs, appears on
│   ├── Songs       (M07–M09)          → flat song table with facets
│   ├── Playlists   (M26–M33)          → Playlist detail → ordered rows
│   ├── Genres      (M08/M38)          → filtered Albums
│   └── Radio       (M61, optional)
├── Sets (unchanged: sets → folders → files, podcasts set)
├── In progress / Continue (unchanged)
├── Downloads (Android, unchanged; gains Music collections M46–M49)
└── Settings (gains Playback, Music library, Remote playback sections)

Global, not a destination:
  Now Playing (player) ── Queue panel/sheet
  Search (/)  → grouped results: Songs · Albums · Artists · Playlists · Files
  Action menu (a / ⋮) on every item
```

Where music data is missing (untagged files, sets without audio) the Music
lens shows an explanatory empty state and the Sets lens keeps working.

**Music scope rule (proposal for M01, decided there):** the Music lens
covers audio files in permitted, non-podcast sets, excluding audiobook files
(`.m4b`, and sets an admin marks as audiobooks). Files without any music tag
appear under Songs with the file-name fallback (§6.4) and under an album
named after their folder, marked *From folder*; they are never silently
dropped.

Queue row action menu (`a`/⋮ on a row, also Shift+F10): Play now, Play next,

- Opening: `Q` or the *Queue* button. Focus moves to the current row. Escape
  (or `Q` again) closes it and returns focus to the opener (button or the
  previously selected library card), using the `modal-focus.js` rules even

  previous track works and the user can see what played.
- Long queues virtualize rendering after 200 rows; the panel shows *Showing
  200 of 1,240 · Jump to now*.

### 6.4 Readable track metadata (both clients)

- Primary line: tag title; fallback = file name **without** extension; never
  invent a title by stripping track numbers.
- Secondary line: track artists (joined with `, `, max 2 then `+N`) · album.
  In album view the album part is omitted; track artist is shown only when it
  differs from the album artist.
- Numbers: `disc-track` only when there is more than one disc.
- Durations in `--font-mono` (web) / tabular figures (Android).
- Technical data (codec, bitrate, sample rate, path) stays in Info (M06),
  never in list rows.
- Long text: 2-line clamp on cards, 1-line ellipsis on rows; the full text is
  in `title`/`aria-label` (web) and semantics label (Android).

## 7. Navigation and state transitions

### 7.1 Web view stack and URLs

Music views extend `navigation-url.js` with `music` and `id` parameters;
existing parameters keep their meaning and can coexist (`media`, filters).

| View | URL | Backspace / ‹ goes to |
| --- | --- | --- |
| Music home | `/?music=home` | previous non-music view |
| Albums | `/?music=albums&sort=artist&genre=…` | Music home |
| Album | `/?music=album&id=al_…` | the list it was opened from (history state), else Albums |
| Artists / Artist | `/?music=artists`, `/?music=artist&id=ar_…` | Artists |
| Songs | `/?music=songs&search=…` | Music home |
| Playlist | `/?music=playlist&id=pl_…` | Playlists |

Each view change pushes one history entry, so the browser Back button and
`Backspace` agree. `media=<id>` keeps restoring the current item; the queue
is restored separately (M16), not from the URL.

### 7.2 Web Escape / Backspace hierarchy (extends the current one)

```
Escape:     text field → blur ▸ hint mode → off ▸ popover/menu → close (focus to opener)
            ▸ dialog (help, playlist picker, settings) → close (focus to opener)
            ▸ Queue panel → close (focus to opener) ▸ fullscreen → exit
            ▸ expanded player → minimize (playback continues) ▸ nothing
Backspace:  same player steps; then music view → parent view (§7.1); then folder → parent
```

### 7.3 Playback state machine (shared by both clients)

```
          play(list, start)            ended & hasNext            ended & !hasNext & repeat=off
 [Idle] ───────────────▶ [Playing] ───────────────▶ [Playing next] ───────────────▶ [Ended]
   ▲                       │  ▲  pause/play                                           │
   │  stop / clear / new   ▼  │                                                       │ play → restart queue
   └────────────────── [Paused] ◀── error: [Error: skip after 1 failure, toast "Couldn't play X — skipped"]
 repeat=one: ended → same track; repeat=all: ended at last → first; sleep timer expires → Paused (M22)
 previous: position > 3 s → restart track; else previous queue item
```

- Selecting, browsing, searching or opening another album never changes
  `[Playing]`.
- A non-audio item (video/image) opened while a music queue plays: video
  pauses the queue and takes the player (as today); the queue is kept and
  *Resume queue* is offered in the mini player. Images never enter a music
  queue (fixes B3).

## 8. Queue ownership and semantics

### 8.1 Ownership

| Concern | Web | Android |
| --- | --- | --- |
| Owner | one `QueueController` module (new `web/js/queue.js`), the single source of "what plays next" for the tab; `playback.js` asks it for next/previous; `playback-nav.js` only **builds** a queue from a listing | `PlayerAudioHandler` (audio_service) owns the queue so it survives screen disposal and drives the notification/lock screen; screens observe it |
| Detached player window | commands posted to the main window (existing `postToDetach` pattern); the main window owns the queue | — |
| Casting | the sender keeps owning the queue and loads the next item on the receiver (M60) | same, via `CastController` |
| Public share pages | a share-local queue (collection shares, M62), never the signed-in user's queue | share viewer has its own queue |
| Scope | per server origin + user id; switching server/account clears the active queue | per saved server + account; switching library stops playback (existing) and keeps that scope's persisted queue |
| Local device files | — | a queue holds items of one source scope (server account **or** device files); mixing is out of scope for v1 |
| Session lease | — | one queue = one `PlaybackSessionCoordinator` claim; starting a video, local file or share stops it, as today |

### 8.2 Insertion semantics (M14/M15/M18/M19)

| Action | Queue result |
| --- | --- |
| Play / Enter / tap on a song in a list | Replace queue with the list's playable audio in displayed order, start at that song. Source label = list name. |
| Play on album/artist/playlist | Replace queue with its songs (album: disc/track order; artist: albums by year then track; playlist: playlist order). |
| Play next | Insert after *Now*, after earlier "Play next" items (FIFO block "Up next (you added)"). |
| Add to queue | Append to the end. |
| Shuffle (on a collection) | Replace queue with the collection shuffled; *Now* = first shuffled item. |
| Shuffle toggle (queue) | Shuffle only upcoming items; turning it off restores the original order of the remaining items. |
| Shuffle by album | Random album order, track order kept inside each album. |
| Files from Sets | Playing a file from a folder builds the queue from that folder's playable items **of the same type** (audio only for audio), so browsing and images no longer affect playback. |
| Multi-selection (M15) | Albums, artists, playlists and search results are the batch unit. Marking several individual songs is decided in M15 (key `m` is reserved for it, §12). |

Duplicates are allowed; each queue entry has its own entry id so remove/move
target the right one.

### 8.3 Resume and progress

- Progress reporting, play counts, favorites, bookmarks and notes stay keyed
  by **media id** and keep working for every item in a queue.
- A song started from a queue starts at 0 unless the item is a podcast
  episode, audiobook or longer than 20 minutes, where the existing resume
  rule (and for podcasts the `uh3` contract) applies. Explicit *Resume at
  m:ss* stays available in Info. Rationale: music listeners expect tracks to
  start from the beginning; long-form audio keeps today's resume.
- The automatic "finished" status of short music tracks must not flood the
  in-progress view; M36/M37 store music plays as listening events instead.

### 8.4 Persistence

- Local (M16): web `localStorage` key `player.queue.<origin>.<userId>` with
  entry ids, media ids, index, position, shuffle/repeat and source label;
  Android the same in its scoped storage. Restored items are revalidated
  against the server (removed/forbidden items are dropped with a quiet
  notice "2 songs are no longer available").
- Server (M17): one saved queue per user, `GET/PUT /api/v1/queue` with a
  revision and an edit clock (last writer wins, same clock rules as
  `docs/podcast-sync-contract.md` §4). Saving is explicit or at pause/exit;
  restoring never replaces an actively playing local queue without asking
  (*Continue from other device?*).

## 10. Identity, API and boundaries

### 10.1 Identities

| Thing | Identity | Notes |
| --- | --- | --- |
| Song / file | existing `media.id` | playback, progress, favorites, bookmarks, notes, tags, shares, downloads keep using it |
| Album | `album_key` (string, e.g. `al_<hash>`) from MusicBrainz release id when present, else normalized (album artist, album title, year/disc-folder) | opaque to clients; never a database row id in URLs |
| Artist | `artist_key` (`ar_<hash>`) from MBID when present, else normalized name | credits keep roles (artist, album artist, composer, performer …) |
| Playlist | `playlist_id` (`pl_<random>`), user-owned | entries have their own `entry_id` to allow duplicates |
| Queue entry | `entry_id` (client-generated UUID) + `media_id` | survives reorder |
| Podcast feed/episode | `feed_key` / `episode_key` from `docs/podcast-sync-contract.md` | unchanged; podcast sets are excluded from the Music lens |

Key stability across retags and moves is A06a (`tk3`); until then keys may
change on retag and clients must treat a missing key as "item removed".

### 10.2 API shape (additive, `handleBoth`, `/api` + `/api/v1`)

```
GET  /api/v1/music/home                         sections for M38/M39
GET  /api/v1/music/albums?sort=&genre=&year=&page=
GET  /api/v1/music/albums/{album_key}           album + ordered songs (disc, track)
GET  /api/v1/music/artists?role=&page=
GET  /api/v1/music/artists/{artist_key}         albums, appears-on, top songs (M40)
GET  /api/v1/music/songs?search=&artist=&album=&genre=&year=&sort=&page=
GET  /api/v1/music/search?q=                    grouped: songs, albums, artists, playlists
GET/POST /api/v1/playlists, GET/PATCH/DELETE /api/v1/playlists/{id}
POST /api/v1/playlists/{id}/entries, PATCH (move), DELETE /…/entries/{entry_id}
GET/PUT  /api/v1/queue                          saved server queue (M17)
```

Every existing media JSON object gains an optional `music` object
(`title, artists[], album_artist, album{key,title}, track, disc, year,
genres[]`); clients fall back to `file_name` when it is absent, so old
clients and non-music media are unaffected. Every music endpoint filters by
the existing set ACL; aggregate counts are per viewer. `docs/api.md` is
updated by the implementing tasks.

### 10.3 Cross-browser remote playback (F02, M59, M60, M71)

Facts: Google Cast's web sender works only in Chrome/Chromium (secure
context); Firefox has no Cast sender, no Remote Playback API and no
Presentation API. The current web code therefore hides the Cast button in
Firefox (`cast.js`), which is correct and must stay.

Design — one **"Play on…"** control on every platform, with targets the
platform can really reach:

| Target type | Chrome | Firefox | Android |
| --- | --- | --- | --- |
| Google Cast receiver | yes (existing sender) | not offered | yes (existing) |
| Another signed-in Player client of the same user (Android app, another browser tab) — "Player Connect" | yes | **yes** | yes |
| Server-side DLNA/UPnP renderer (M59, server acts as control point) | yes | yes | yes |

Player Connect: clients that opt in register as playback targets
(`POST /api/v1/remote/sessions`, heartbeat; listed by
`GET /api/v1/remote/sessions`), and receive commands over a server event
stream (SSE): load queue, play, pause, seek, next, previous, volume. The
controlling client shows the remote state in its mini player
("Playing on Pixel 7"). This gives Firefox users a supported way to play on
the Android app — and through it on a Chromecast — and is the same
mechanism as M71's live listener view. In Firefox the control is a button
labeled **Play on…**; with no targets the menu says "No playback devices
found. Open Player on another device and sign in to control it from here."
Nothing in Firefox imitates Cast.

### 10.4 Coordination with podcasts (`uh3` and follow-ups)

- Podcast sets are not part of the Music lens; podcast episodes are not
  album/artist entities.
- A podcast episode may be queued as a generic media item; its start
  position and completion follow the podcast contract (§4.2 and §8 there),
  not music rules. Queue code must call the existing progress endpoints so the
  server mirrors episode state as specified in that contract (§7.1 there).
- The global **Sync now** coordinator (`zh3`) may later carry the saved
  queue (M17) and listening events (M37); they use the same edit-clock and
  pending-edit rules and add no new feedback UI beyond `4i3`'s quiet hint.

## 13. Accessibility and focus rules (both clients)

- Web: every new control is a `button`/`a`/native form element with a
  concise accessible name ("Play next: Harbour"); toggles use
  `aria-pressed`; the queue is a `role="list"` with the current item marked
  `aria-current="true"`; announcements (added, removed, now playing) go
  through the existing `role="status"` toast. Focus is never lost: after
  actions it stays on the acted-on item, after dialogs it returns to the
  opener, after removals it moves to the item now at that position.
- Android: `Semantics` labels on artwork and mini player, `tooltip` on icon
  buttons (existing pattern), custom semantics actions *Move up* / *Move
  down* / *Remove* on queue rows, 48 dp minimum, text scales to 200 %
  without clipping (rows wrap instead of truncating essential labels).
- Contrast 4.5:1 for text in light and dark; check every new overlay on
  artwork in both themes.

## 14. Verification approach for dependent tasks

Each dependent task follows its row in the candidate map and:

1. Uses a disposable local server and the shared tagged fixture from `oj3`
   (Music V01) — the fixture described in §2 is the minimum.
2. Runs the journey in installed Google Chrome (codec-capable, Playwright
   `channel: chrome`), installed Mozilla Firefox (Playwright `moz-firefox`
   channel with `executablePath` of the installed binary; Playwright's
   bundled Firefox does not count), and the release APK on an Android
   emulator via `adb`/`uiautomator` (`test/e2e-live/adrv.py`) or
   `integration_test` where it drives the real app.
3. Proves the effect, not just the UI: media element/`currentSrc` and
   `currentTime`, Android `dumpsys media_session` state/metadata, API state
   after reload/restart.
4. Captures light, dark and narrow screenshots outside the repository and
   records exact versions and commands in the task annotations.
5. States every gap (e.g. audio output not heard, no real Cast receiver,
   no Android Auto head unit) and keeps the feature unaccepted on that
   platform.
