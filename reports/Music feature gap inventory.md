# Build Player's music backlog from evidence

Player's largest music gaps are **a metadata-based music library, a real playback queue, persistent playlists, and Android track sequencing**. Its web player advances through the current browse view; that is useful, but it is not an editable queue. Its Android player loads **one item at a time**: notification next/previous currently seek ±15 seconds rather than changing tracks. Navidrome, DSub2000 and Tempo provide a much broader music model around albums, artists, queues, discovery, ratings and listening data. Player already has lyrics, file favorites, covers, downloads, resume, bookmarks, search, sharing and some casting, so those should be extended only where a specific gap exists. The tables below inventory the reference products and turn their confirmed differences into implementation candidates; they are a source comparison, not a claim that every hidden feature or runtime behavior has been exhaustively tested.

## Scope and snapshots

Observed **2026-10-20**: [Navidrome 0.64.2](https://github.com/navidrome/navidrome/releases/tag/v0.64.2), [DSub2000 5.7.5](https://github.com/paroj/DSub2000/releases/tag/5.7.5), and [Tempo 3.9.0](https://github.com/CappielloAntonio/tempo/releases/tag/3.9.0). Tempo here means **CappielloAntonio/tempo**, not the separate Tempus successor/fork. Tempo's 3.9.0 release contains a stale Gradle version name of 3.8.1; the release record defines the snapshot. Player was inspected at Git HEAD `5040cfb3fac80e3d413369997c13f273fde33267`.

Reference-product evidence comes from official documentation and pinned release source. Player status comes from source inspection. **No Chrome, Firefox, Android device/emulator, audio-output, or runtime feature checks were performed for this inventory.** Server-dependent client actions are conditional on a compatible server and permissions. Cast and Android Auto also depend on app build flavor and platform support.

## Suggested first wave and completion criteria

Start with **M01–05, M12–18, M20 and M54**: establish stable music metadata/entities, implement an independent shared queue model, then make Android actual track transitions and OS music controls work. Add album/artist navigation and music search around those foundations, followed by persistent playlists and offline collection behavior. This is a dependency-based proposal, not a priority commitment or task creation. ReplayGain, discovery, richer sharing and integrations can then consume reliable song/album/artist and queue identities instead of reproducing file-browser assumptions.

The backlog is source-grounded, but **runtime verification is still open on every platform**. For each selected feature, exercise actual playback and state changes in **Google Chrome, Mozilla Firefox and the native Android app on a device/emulator** before calling it complete. Include native notification/headset track controls when sequencing changes, reload/restart/restore when persistence changes, and loss-of-network tests when offline behavior changes. Android-only system integrations need Android checks and an explicit statement of their platform scope; browser limitations such as Cast need a concrete supported design. This follows the repository's [feature parity instructions](/home/paul/git/player/AGENTS.md:13). No code, tasks, commits, releases or test runs were created by this research report.
